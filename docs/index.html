Unitree G1 を VLM で動かすロードマップ

カメラ画像と言葉の指示から、実機の G1 が「見て、考えて、歩いて、止まる」まで。安全を先に固め、シミュレーション、提案モード、自動モードの順に権限を広げていきます。

情報は 2026 年 11 月時点のものです。SDK やファームウェア、モデルは頻繁に更新されるので、実施前に各リンク先で最新を確認してください。

考え方

このロードマップは、G1 を「言葉で指示すると、カメラで周りを見て歩き、目的の場所で止まる」状態にすることをゴールにしています。腕を使った物体操作は、歩行がしっかり動いてからの発展課題（フェーズ 7）にしています。

  • VLM は「どこへ・どれだけ」だけを決める二足歩行のバランスは G1 内蔵の歩行制御がすでに解いています。VLM には速度指令に落とせる粒度の判断だけを任せ、学習データを集めずに始められる構成にします。
  • VLM の出力は決められた JSON に限り、実行前に必ず検査する形式違反や上限超えは停止に置き換えます。1 回の指令は 1 秒で失効させ、次の指令が来なければロボットは自然に止まります。
  • 権限は段階的に広げるシミュレーション、人が 1 手ずつ承認する提案モード、自動モードの順に進めます。各フェーズの完了条件を満たすまで次へ進みません。

システム構成

最終的に目指す構成です。最初（フェーズ 3〜5）は実行器を有線 LAN でつないだ開発 PC で動かし、フェーズ 6 で G1 の開発用コンピュータ（PC2）へ移します。こうすると Wi-Fi が切れても、ロボットのすぐそばで停止判断ができます。

VLM と VLA の違い

機械学習の予備知識がなくても読めるように、このロードマップで登場する 2 種類のモデルを整理しておきます。

VLM（Vision-Language Model）

画像と文章を入力すると、文章を出力するモデルです。ロボットを直接は動かせないので、出力した文章（ここでは JSON）を自分のプログラムで速度指令に変換します。

大量の画像と文章であらかじめ学習済みなので、プロンプトを書くだけで使い始められます。1 回の推論に 0.5〜数秒かかるため、細かい動作の制御には向きません。

VLA（Vision-Language-Action Model）

画像と文章を入力すると、関節角度などのロボットの動作を直接出力するモデルです。毎秒数回から数十回の速さで動作を出し続けます。

自分のロボットと自分のタスクで動かすには、たいてい人が遠隔操作して集めた実演データで追加学習（ファインチューニング）が必要です。学習用の GPU も要ります。

G1 にはすでに安定した歩行制御が入っているので、「前へ 0.2 m/s で 1 秒」のような指令さえ出せば歩けます。そのため、データ収集なしで始められる VLM から入り、VLM が苦手な手先の操作が必要になった段階で VLA を検討する、という順番にしています。脚ロボットの言語ナビゲーション研究の NaVILA も、VLM に「75 cm 前進」のような中間レベルの言葉の行動を出させ、低レベルの歩行は別の制御器に任せる 2 層構成をとっています。

始める前に

機体

  • G1 EDU が必要です。標準の G1 は SDK による二次開発に対応していません。EDU には開発用コンピュータ PC2（Jetson Orin NX 16GB）が載っています。
  • 頭部には Livox MID-360（3D LiDAR）と Intel RealSense D435i（深度カメラ）が付いています。このロードマップでは D435i の画像を VLM に渡します。
  • 2026 年 9 月に首の関節やデュアルカメラを加えた改良版 G1+ が発表されたと報じられています。G1+ を使う場合は、フェーズ 4 のカメラまわりを機体に合わせて読み替えてください。
  • ファームウェアのバージョンを最初に記録しておきます。SDK の挙動がファームウェアによって変わることがあります。

計算機

  • 開発 PC：Ubuntu 22.04 を推奨します。ROS 2 を併用するなら Humble（unitree_ros2 の推奨環境）。有線 LAN ポートが必要です。
  • GPU PC：ローカルで VLM を動かす場合に使います。VRAM 24GB クラス（RTX 3090 など）があれば 4B〜9B 程度のモデルを動かせます。クラウド API だけを使うなら不要です。

設備と人

  • G1 を吊るせる安全クレーン（ガントリー）と、平らで障害物のない広い床。
  • 操作者と、リモコンを持って停止だけを担当する監視者の 2 人体制。

ロードマップ

0

安全と運用ルールを決める

1 週間

プログラムを書く前に、リモコンだけで G1 を安全に立たせ、歩かせ、止められるようにします。

やること

  1. 公式の G1 SDK Development Guide の Quick Start とリモコン操作の章を読みます。
  2. クレーンで吊った状態での起動、立ち上がり、歩行、減衰（Damp）、吊り下げ停止の手順を通しで練習します。
  3. 状態遷移（FSM）を体で覚えます。たとえば腕を SDK で動かすにはロックスタンド（メイン運動制御）に入っている必要があり、デバッグモードに入ると内蔵の運動制御が完全に止まって高レベル API が使えなくなります。
  4. 運用ルールを紙 1 枚にまとめて掲示します。最高速度、作業エリア、役割分担、非常時の手順を書きます。

安全ゲート

  • 減衰（Damp）はその場で関節の力を抜く操作です。立っている G1 は崩れ落ちるので、クレーンなしで減衰させないこと。
  • リモコンのボタンの組み合わせはファームウェアや資料によって違うことがあります。必ず手元の機体の公式マニュアルで確認してください。
  • 最初は速度上限を前後 0.3 m/s、旋回 0.3 rad/s 程度に決めておきます（SDK のサンプルが使っている値）。

完了条件

1

開発 PC と G1 をつなぎ、状態を読む

1 週間

開発 PC から G1 の IMU と関節角度を読めるようにします。まだ何も動かしません。

やること

  1. 開発 PC と G1 を LAN ケーブルでつなぎ、開発 PC の有線 NIC を 192.168.123.99 / 255.255.255.0 に固定します（例。同じサブネットで空いている番号なら可）。
  2. 疎通を確認します。PC1（運動制御）は .161、PC2（開発用 Jetson）は .164 です。
  3. unitree_sdk2_python を入れます。CycloneDDS が見つからないと言われたら、README の手順で CycloneDDS 0.10.x をビルドし、CYCLONEDDS_HOME を設定します。
  4. rt/lowstate トピックを購読して、IMU と関節角度を表示・記録します。G1 のメッセージ型は unitree_hg です（Go2 などの unitree_go とは別）。
  5. ROS 2 で扱いたい場合は unitree_ros2 を入れ、setup.sh の CYCLONEDDS_URI に NIC 名を書きます。
# 疎通確認
ping 192.168.123.161
ping 192.168.123.164
ssh unitree@192.168.123.164

# Python SDK のインストール
git clone https://github.com/unitreerobotics/unitree_sdk2_python.git
cd unitree_sdk2_python
pip3 install -e .

状態を読むだけの最小コードです。引数には G1 につながっている NIC 名（ip a で確認。例 enp3s0）を渡します。

# read_state.py
import sys
import time
from unitree_sdk2py.core.channel import ChannelSubscriber, ChannelFactoryInitialize
from unitree_sdk2py.idl.unitree_hg.msg.dds_ import LowState_

def on_state(msg: LowState_):
    r, p, y = msg.imu_state.rpy
    print(f"roll={r:+.3f} pitch={p:+.3f} yaw={y:+.3f}  q0={msg.motor_state[0].q:+.3f}")

ChannelFactoryInitialize(0, sys.argv[1])
sub = ChannelSubscriber("rt/lowstate", LowState_)
sub.Init(on_state, 10)
while True:
    time.sleep(1.0)
python3 read_state.py enp3s0

つまずきやすい点

  • DDS は 192.168.123.x の NIC 1 つだけにバインドさせます。Wi-Fi や USB-LAN が混ざると探索に失敗しやすくなります。
  • 起動直後は DDS の探索に少し時間がかかります。最初の数秒は値が来なくても慌てないこと。

完了条件

シミュレーションでロボットの「口」を作る

2 週間

上位のプログラムから見たロボットの窓口（インタフェース）を決め、シミュレーションで中身を差し替えながら動かせるようにします。

やること

  1. ロボットの窓口を 1 つのクラスに決めます。move(vx, vy, wz, duration)、stop()、gesture(name)、get_image()、get_state() の 5 つで十分です。
  2. 中身を 3 種類用意します。ログを出すだけのモック、MuJoCo のシミュレーション、実機（フェーズ 3）。設定 1 行で切り替えられるようにします。
  3. MuJoCo 版には unitree_rl_gym の G1 歩行ポリシーを使います。deploy_mujoco.py は速度指令が設定ファイルの固定値（cmd_init）なので、外から指令を受け取れるように改造します。
  4. MuJoCo のシーンにも頭の位置にカメラを置き、画像を取り出せるようにします。フェーズ 5 の VLM をまずここで試します。
# G1 歩行ポリシーを MuJoCo で動かす（sim2sim）
# 依存関係（MuJoCo など）は README に従って先に入れておく
git clone https://github.com/unitreerobotics/unitree_rl_gym.git
cd unitree_rl_gym
python deploy/deploy_mujoco/deploy_mujoco.py g1.yaml

注意：G1 内蔵の歩行制御（sport サービス）はシミュレーションには入っていないので、LocoClient はシミュレーションでは応答しません。そのため MuJoCo 版では強化学習の歩行ポリシーを代役にします。腕の操作を扱うフェーズ 7 では、実機と同じ DDS インタフェースを持つ Isaac Lab ベースの unitree_sim_isaaclab も候補になります。

完了条件

3

実機で歩行 API を叩く

1 週間

フェーズ 2 で決めた窓口の実機版を作り、スクリプトから G1 を歩かせて止めます。

やること

  1. まず公式サンプル g1_loco_client_example.py がそのまま動くことを確認します。動かない場合はファームウェアとの組み合わせを疑います（SDK の速度指令が効かないファームウェアがあるという報告もあります）。
  2. LocoClient の主な API を確かめます。立ち上がりは Damp() の後に Squat2StandUp()、移動は SetVelocity(vx, vy, omega, duration)、停止は StopMove()、手振りは WaveHand() です。
  3. Move(vx, vy, vyaw) は既定で 1 秒だけ有効な速度指令を送ります。この「放っておけば止まる」性質を安全設計の土台にします。
  4. 腕のプリセット動作は G1ArmActionClient で呼べます（"shake hand"、"high five"、"clap"、"release arm" など）。VLM に「手を振る」「握手する」を選ばせるときに使います。
  5. 符号を実機で確かめます。vy と omega の正の向きを、クレーン下でゆっくり動かして記録します。
# 公式サンプル（クレーン下で、周りに何もないことを確認してから）
cd unitree_sdk2_python
python3 example/g1/high_level/g1_loco_client_example.py enp3s0

実機版の窓口の骨組みです。上限のクリップと 1 秒失効をここで強制します。

# g1_vlm/robot/real.py（例）
from unitree_sdk2py.core.channel import ChannelFactoryInitialize
from unitree_sdk2py.g1.loco.g1_loco_client import LocoClient
from unitree_sdk2py.g1.arm.g1_arm_action_client import G1ArmActionClient, action_map

LIMITS = {"vx": 0.3, "vy": 0.2, "wz": 0.3}   # m/s, m/s, rad/s
MAX_DURATION = 1.0                           # 1 回の指令は 1 秒で失効

def clamp(v, lim):
    return max(-lim, min(lim, v))

class RealG1:
    def __init__(self, nic: str):
        ChannelFactoryInitialize(0, nic)
        self.loco = LocoClient()
        self.loco.SetTimeout(10.0)
        self.loco.Init()
        self.arm = G1ArmActionClient()
        self.arm.SetTimeout(10.0)
        self.arm.Init()

    def move(self, vx, vy, wz, duration=1.0):
        return self.loco.SetVelocity(clamp(vx, LIMITS["vx"]),
                                     clamp(vy, LIMITS["vy"]),
                                     clamp(wz, LIMITS["wz"]),
                                     min(duration, MAX_DURATION))

    def stop(self):
        self.loco.StopMove()

    def gesture(self, name):
        if name not in action_map:
            raise ValueError(f"unknown gesture: {name}")
        self.arm.ExecuteAction(action_map[name])

安全ゲート

  • 最初はクレーンで体重を少し支えた状態で、次にクレーンを緩めて（外さずに）試します。
  • 開発 PC の LAN ケーブルを抜いたとき、1 秒以内に止まることを必ず確かめます。
  • 高レベル API はデバッグモードでは無効です。低レベル制御のサンプルと混ぜて使わないこと。

完了条件

頭部カメラの画像を取り出す

1 週間

頭部の D435i の画像を、タイムスタンプ付きで VLM を動かすマシンまで届けます。

やること

  1. D435i は PC2 につながっています。PC2 で画像を取り、ネットワーク越しに配信します。
  2. 方法は 2 つあります。(a) Unitree の teleimager（UVC・OpenCV・RealSense のカメラを ZeroMQ または WebRTC で配信する画像サーバ。xr_teleoperate でも使われています）。(b) PC2 で pyrealsense2 などを使って自作し、JPEG を ZeroMQ で送る。
  3. VLM に渡すには 640×480 の JPEG で十分です。撮影時刻と受信時刻を記録し、遅延を測ります。
  4. 深度画像も取れるようにしておきます。フェーズ 6 で「正面 0.8 m 以内に何かあれば止まる」という、VLM に頼らない安全判定に使います。

5

VLM を提案モードでつなぐ

2 週間

VLM に画像と指示を渡して次の行動を JSON で提案させ、人が承認したものだけを実行します。

やること

  1. 行動の種類を固定します。move（速度と時間）、stop、gesture（腕のプリセット名）、done（達成）、ask（指示が曖昧なときの質問）の 5 つから始めます。
  2. 出力の JSON 形式を決め、システムプロンプトにロボットの座標系・上限・行動の種類を書きます。
  3. バリデータを作ります。JSON として読めない、知らない行動、上限超え、のどれかに当たれば stop に置き換えます。
  4. 提案モードを作ります。VLM の提案と画像を画面に出し、人が Enter を押したときだけ実行します。
  5. 画像・プロンプト・VLM の返答・実際に送った指令をすべて記録し、あとで再生できるようにします。
  6. まず MuJoCo で、次にクレーン下の実機で試します。

VLM に返させる JSON の例です。

{
  "action": "move",
  "vx": 0.2,
  "vy": 0.0,
  "wz": 0.0,
  "duration": 1.0,
  "reason": "椅子が正面の約 2 m 先に見えるので前進する"
}

システムプロンプトのたたき台です。

あなたは人型ロボット G1 の次の行動を決める係です。
入力：頭部カメラの画像 1 枚、ユーザーの指示、これまでの行動の履歴。
出力：次の 1 秒の行動を JSON 1 個だけ。JSON 以外は書かない。
座標：vx は前、vy は左、wz は左回りが正（単位 m/s と rad/s）。
上限：|vx| ≤ 0.3、|vy| ≤ 0.2、|wz| ≤ 0.3、duration ≤ 1.0。
行動：move / stop / gesture / done / ask のいずれか。
人や障害物が 1 m 以内に見えたら stop を返す。
指示を達成したら done、指示が分からなければ ask を返す。

座標の符号はフェーズ 3 で確かめた実機の向きに合わせて書き換えてください。「画像の右」と「ロボットの右」を VLM が取り違えることはよくあるので、正解が分かっている場面の画像で先にテストします。

完了条件

6

閉ループで自動実行する

3 週間

「観測、判断、短く実行、また観測」を自動で回し、簡単な移動タスクを人の承認なしで達成させます。

やること

  1. 提案モードの承認を外し、1 Hz 前後でループを回します。1 回の実行は 1 秒以内に限ります。
  2. VLM に頼らない安全ゲートを実行器に入れます（下の囲み）。
  3. 実行器を PC2 に移します。GPU PC との通信が切れても、PC2 が自分で止まれるようにするためです。
  4. タスクを決めて評価します。たとえば「前方の椅子の前まで行って止まって」「右を向いて、人がいたら手を振って」「ドアを探して、その前で止まって」。
  5. 達成の判定も VLM に任せ（done）、判定が正しかったかを人が記録します。
# ループの骨組み（擬似コード）
while not finished:
    frame = camera.latest()                      # 画像＋深度＋タイムスタンプ
    if safety.too_close(frame.depth):            # VLM とは独立に判定
        robot.stop()
        continue
    reply = vlm.decide(frame.color, instruction, history)
    cmd = safety.validate(reply)                 # 形式・種類・上限。ダメなら stop
    if mode == "propose" and not operator.approve(cmd, frame):
        robot.stop()
        continue
    robot.execute(cmd)                           # 1 秒で失効する指令
    history.append(cmd)
    log.save(frame, reply, cmd)
    finished = cmd.action == "done" or len(history) >= MAX_STEPS

安全ゲート（VLM に頼らない部分）

  • ウォッチドッグ：有効な指令が一定時間（例 1.5 秒）来なければ StopMove()。
  • 近接停止：深度画像の中央付近に 0.8 m 以内の物体があれば停止。
  • 手数の上限：1 タスクあたりの最大ステップ数を決め、超えたら停止して人に返す。
  • デッドマン：操作者がキーやボタンを押している間だけ動く仕組みを、自動モードの初期は残しておく。
  • リモコン：監視者はいつでもリモコンで止められる位置にいる。

完了条件

7

腕の操作と VLA へ発展させる

継続

移動の次に、腕を使ったタスクへ広げるための選択肢を整理します。ここから先はテーマに応じて選びます。

腕を自分で動かす

  • プリセット動作：G1ArmActionClient の動作を VLM に選ばせる。フェーズ 3 で用意済み。
  • arm_sdk：rt/arm_sdk トピックに LowCmd_ を送り、内蔵の歩行制御を動かしたまま腕と腰の関節を PD 指令で動かす。ロックスタンドに入っていることが条件で、関節番号 29 の q に 0〜1 を入れて内蔵制御とのブレンド率を指定する。独自に腕を動かすときは、内蔵の腕アクションサービスを止める必要がある。
  • 逆運動学（IK）：SDK はデカルト座標での指令を直接は持たないので、手先の目標位置から 7 関節の角度を計算する。xr_teleoperate は Pinocchio を使っている。VLM が画像上で指した点と深度から 3 次元の目標位置を作れば、「それを取って」の第一歩になる。

VLA を使う

  • UnifoLM-VLA-0（Unitree、2026 年 1 月公開）：Qwen2.5-VL-7B を基にした VLA。G1 の 12 種類の操作タスク（引き出しの開閉、プラグの抜き差し、ピック＆プレースなど）を単一のポリシーでこなしたと報告。重みとデータセットが Hugging Face にある。
  • GR00T N1.6（NVIDIA）：3B パラメータの人型ロボット向け VLA。事前学習データに G1 の全身移動操作が含まれ、G1 のピック＆プレース用ファインチューニング済みチェックポイントもある。
  • GR00T 2 / GR00T 2 Turbo（NVIDIA、2026 年 11 月発表）：未来の映像と行動を同時に予測する world action model。Turbo を G1 で動かすデモでは、推論は Jetson AGX Thor、全身制御は別の Jetson Orin NX で行っている。重みは 12 月に公開予定とされている。
  • データ収集：xr_teleoperate（Apple Vision Pro・PICO・Quest で遠隔操作し記録）で実演を集め、unitree_lerobot で学習・評価する流れが公式に用意されている。シミュレーションでは unitree_sim_isaaclab でデータ収集や検証ができる。

現実的な発展形は、VLM を「計画する係」、VLA を「1 つの技能を実行する係」とする組み合わせです。たとえば VLM が「棚の前まで歩く」「赤い箱を取る」「台に置く」と分解し、歩行は内蔵制御、「赤い箱を取る」は VLA に任せます。

完了条件（次の判断材料）

モデルの選び方

VLM の呼び出し部分は差し替えられるように作っておき、最初はローカルとクラウドの両方を試して比べるのがおすすめです。

候補動かす場所向いている点注意点
Gemini Robotics ER 2 クラウド API（gemini-robotics-er-2-preview、低遅延版の -streaming-preview） ロボット向けの空間推論。画像上の物体を [y, x]（0〜1000 に正規化）で指せる。関数呼び出しで自作のロボット API を呼ばせられる。 プレビュー版で、前の版（ER 1.6）は 2026 年 8 月に提供終了済み。通信が必要。人が写る画像を外部に送るので、写る人の同意が要る。
Qwen3.5 GPU PC でローカル実行（vLLM や SGLang で OpenAI 互換 API として立てる） オープンウェイト（Apache 2.0）で、0.8B から 397B まで揃う。通信不要で、画像を外に出さない。追加学習もできる。 VRAM 24GB なら 4B〜9B 程度が現実的。小さいモデルほど空間の判断が弱いので、プロンプトと検査で補う。
汎用のクラウド VLM 各社の API 指示の解釈や会話が得意。試作が速い。 ロボット専用ではないので、座標や距離の推定は要検証。遅延と費用。
PC2 上の小型 VLM G1 の Jetson Orin NX 16GB ネットワークに依存しない。 メモリと速度が厳しく、画像配信や実行器と取り合いになる。まずは外部の GPU PC で始め、最後に検討する。

G1 で VLA を使う場合の候補（UnifoLM-VLA-0、GR00T など）はフェーズ 7 を参照してください。

リスクと対策

リスク対策
転倒クレーン、低い速度上限、平らな床、作業エリアの区切り。減衰はクレーン下でのみ。
VLM の誤判断行動の種類を固定、JSON 検査と上限クリップ、1 秒失効、提案モードで十分に試してから自動化。
判断の遅さ止まって考え、短く動く方式にする。1 回の実行は 1 秒以内、ループは 1 Hz 前後。
通信断ロボット側（PC2）のウォッチドッグで停止。速度指令自体も 1 秒で失効。
左右・座標の取り違えプロンプトに座標系を明記し、正解の分かる場面でテスト。符号は実機で確認した値を使う。
ファームウェア更新で API の挙動が変わるバージョンを記録し、更新後は公式サンプルとフェーズ 3 の停止テストをやり直す。
プライバシークラウド VLM に人が写る画像を送る場合は事前に同意を得る。ローカル VLM を選ぶ選択肢も残す。

用語集

PC1 / PC2
G1 EDU の中のコンピュータ。PC1（192.168.123.161）は運動制御を担当し、ユーザーは触りません。PC2（192.168.123.164）は開発用の Jetson Orin NX で、自分のプログラムを置けます。
DDS / CycloneDDS
G1 の通信の仕組み。ROS 2 と同じ方式で、同じネットワーク上のプログラム同士がトピック名でデータをやりとりします。unitree_sdk2 は CycloneDDS 0.10.x を使います。
LocoClient
G1 内蔵の歩行制御（sport サービス）を呼び出すための SDK のクラス。立ち上がり、速度指令、停止、手振りなどができます。
FSM（状態遷移）
G1 が今どのモードにいるか。減衰、ロックスタンド、歩行などのモードがあり、モードによって受け付ける指令が変わります。
減衰（Damp）
関節の力を抜いて、柔らかく抵抗するだけの状態にすること。立っている G1 は崩れるので、クレーン下で使います。
デバッグモード
内蔵の運動制御を完全に止め、低レベル（関節）制御を自分で行うためのモード。このモードでは LocoClient などの高レベル API は使えません。
arm_sdk
内蔵の歩行制御を動かしたまま、腕と腰の関節だけを自分で動かすための DDS トピック（rt/arm_sdk）。
sim2sim / sim2real
あるシミュレータで作った制御を別のシミュレータや実機に移すこと。移した先で挙動が変わることが多いので、段階を踏んで確かめます。
ファインチューニング
学習済みのモデルを、自分のデータで追加学習して特定の用途に合わせること。
